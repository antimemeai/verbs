# Lane: algebraic data types

Date: 2026-11-23. Habit under study: favor algebraic data types (sum types,
product types, illegal states made unrepresentable). This report covers the
constructs that carry the habit in C++ and Rust, the existing guards around
them, the patterns that signal "this should have been an ADT", and what was
measured on this machine. It does not write the design.

Toolchains used for every probe below:
- C++: Homebrew clang 23.1.2 (`/opt/homebrew/Cellar/llvm/23.1.2/bin/clang++`),
  its own libc++, `-std=c++2c -isysroot $(xcrun --show-sdk-path)`. Without
  the explicit `-isysroot` the configured sysroot
  (`CommandLineTools/SDKs/MacOSX26.sdk`) is missing and linking fails with
  `library not found for -lc++`.
- Rust: rustc/clippy 1.99.1 (`clippy 0.1.99 (58cf8f9c35 2026-10-13)`). The
  repository's `rust-toolchain.toml` pins `1.99.0`, a different build
  (`rustc 1.99.0 (b940084d7 2026-09-28)`, `clippy 0.1.99 (b940084d7e)`), so
  probes run with a bare `cargo clippy` inside the repo use 1.99.0, not
  1.99.1. Plus `nightly-2026-08-21`
  (`rustc 1.100.0-nightly (8925ea358 2026-08-20)`) for one unstable lint.

Artifacts (ignored, under `context/scratch-adt/`):
- `probes/`: every C++ probe (`p1`–`p7`, `m1`–`m4`, `o1`–`o3`, `sw.cpp`,
  `ex.cpp`, `ct_*.cpp`), the two construct prototypes `match.h` and
  `match2.h`, and the wrapper `cxx.sh`.
- `tools/`: `census.py` (text census), `mkdb.py` (compile-database rewrite),
  `agg.py` and `boolrecs.py` (AST census aggregation); `q.txt` holds the
  clang-query matchers.
- `census.txt`, `agg.json`, `boolrecs.tsv`: the corpus results quoted below.
- `refs/`: the P2688R6 HTML and its text extraction.

The extracted corpus trees (662 MB) and the clang-query logs (123 MB) were
deleted after the run.

## Findings in brief

1. **C++ already has a compile-time exhaustiveness stop: `std::visit` with an
   overload set.** A missing alternative is ill-formed. What it lacks is a good
   message and protection from three silent bypasses: a catch-all `auto` arm,
   an arm reached through implicit conversion, and dispatch written as
   `get_if`/`holds_alternative`/`index()` chains. All three compiled with no
   diagnostic on clang 23.1.2 (§1.1).
2. **A small owned `match` over `std::variant` can turn all three bypasses into
   compile errors that name the offending alternative**, with no analysis
   infrastructure. A 30-line prototype did this. The diagnostic fell from 72
   lines and 10.7 KB, naming no type, to 23 lines and 1.7 KB naming `Tri`
   (§1.2). A reasoned `otherwise` arm with a compile-time staleness check also
   works (§5).
3. **Rust needs no construct.** rustc makes a non-exhaustive `match` a hard
   error. Clippy already ships the nearest guards:
   - `wildcard_enum_match_arm` and `match_wildcard_for_single_variants`;
   - `struct_excessive_bools` and `fn_params_excessive_bools`;
   - `option_option`, `unnecessary_unwrap`, `allow_attributes_without_reason`;
   - `#[expect(..., reason)]` with `unfulfilled_lint_expectations`.

   All of these fired in the probes. Two gaps remain: no lint for an
   `if let` chain over enum variants, and none for stringly or sentinel code
   (§2).
4. **C++ pattern matching (P2688) is not available.** EWG did not forward it
   for C++26 at Hagenberg (poll 20/11/6/13/5), and it now targets C++29. A
   Clang prototype exists on a fork branch behind `-fpattern-matching`;
   clang 23.1.2 rejects that flag. Its exhaustiveness rules are still the best
   available specification of what a C++ sum-type guard should say (§1.5).
5. **C++26 reflection is not usable on the pinned clang 23.1.2.**
   - The driver ignores `-freflection`, and `<meta>` does not exist.
   - `-Xclang -freflection` parses `^^` but rejects `^^E` for an enum
     ("unknown or unimplemented reflectable entity").
   - Expansion statements (`template for`) do compile and run, but
     `__cpp_expansion_statements` is undefined.

   So enum-exhaustiveness-by-reflection is not available on this toolchain.
   Variant exhaustiveness does not need reflection anyway (§1.6).
6. **The "should have been an ADT" patterns split sharply by evidence
   quality.** On 8 corpus projects (60 sampled TUs each):
   - **Enum plus union in one record (structural tagged union).** 10 of 10
     distinct first-party matches were genuine tagged unions. Several have a
     real reason not to become `std::variant`: C ABI, constexpr layout, and
     the like.
   - **Records with 4+ bools, clippy's rule.** Of 46 distinct sampled
     records, about 13 (≈28%) contain a sub-cluster that encodes a mode or
     state. Almost none is an ADT as a whole; the rest are independent
     option or capability flags.
   - **Strings compared against 3+ literals.** About 10–12 of 39 first-party
     sites carry an internal string-coded variant. The rest are boundary
     parsing.

   These are one reader's labels (§3).
7. **Existing C++ lint coverage of this habit is thin.**
   - clang-tidy has `bugprone-tagged-union-member-count` (count mismatch
     only), `cppcoreguidelines-pro-type-union-access` (every union access)
     and `bugprone-unchecked-optional-access` (optional only).
   - Nothing in clang-tidy is specific to `std::variant` misuse, unchecked
     `std::expected`, bool clusters, stringly variants, sentinel returns or
     `dynamic_cast` chains.
   - Two generic checks touch variant dispatch, both pushing toward a
     catch-all (added by check). `bugprone-switch-missing-default-case`
     fires on `switch (v.index())` with no default.
     `bugprone-unhandled-code-paths` (`WarnOnMissingElse`) fires on an
     `else if` chain with no final `else`.
   - The proprietary Sonar rule RSPEC-6000 targets `index()` switches and
     `holds_alternative`/`get_if` chains directly. No precision figures are
     published for it.
   - The Core Guidelines list "Enforcement: ???" for C.181 (naked unions) and
     C.153 (prefer virtual to casting).
8. **The best published detector for one of these patterns is expensive and
   whole-program.** Urcrat (Hong & Ryu, ASE 2024) finds C union tag fields
   with no false positives (74 of 79 found, 5 missed) over 36 programs. It
   needs a points-to analysis, and gawk took 4,910 s.
9. **No evidence exists on agent behavior specific to ADT guards.** The
   nearest data:
   - RustAssistant (GPT-4) fixed 208/291 (71.5%) of clippy *pedantic*
     findings, against 76/291 (26.1%) for clippy's auto-fix.
   - Practitioner reports say agents clear lint failures by suppression.

   In ADT terms, the suppression move is the catch-all arm.

## 1. C++ constructs

### 1.1 `std::variant` + `std::visit`

**How it works (libc++ 23.1.2).**
- `std::visit(f, v)` builds a constexpr table of dispatch functions, one per
  alternative index, and calls through the entry for `v.index()`.
  - Each entry invokes `f` on that alternative, so every alternative must
    have a viable overload of `f`, or the program is ill-formed.
  - That is the exhaustiveness guarantee, and it is a compile error today.
- Before dispatching, `visit` calls `__throw_if_valueless`
  (`quarantine/llvm-project/libcxx/include/variant:1585-1604`). A valueless
  variant throws `bad_variant_access`.
- `valueless_by_exception()` is `index() == variant_npos` (`variant:744`).

**Probes (`context/scratch-adt/probes/`, all `-Wall -Wextra`):**

| Probe | Code shape | Result on clang 23.1.2 |
|---|---|---|
| `p1_missing` | overload-set visitor lacks `Tri` | error, **72 lines, 10,774 bytes**; primary error is `no matching function for call to '__invoke'` inside `variant:547`; the alternative is identified only as `__dispatcher<2>`; `Tri` appears only inside template argument dumps |
| `p2_catchall` | `[](const Circle&)…, [](const auto&){ return 0.0; }` | compiles, no diagnostic; `Square` and any future alternative go to the catch-all |
| `p3_conv` | `variant<int,bool,std::string,char>` visited by `[](long)`, `[](const std::string&)` | compiles, no diagnostic; running it prints `long` for both `V{true}` and `V{'x'}`: `int`, `bool`, `char` all reach the `long` arm by conversion |
| `p4_ifconstexpr` | generic lambda with `if constexpr (is_same_v<T,A>) … else return 0;` | compiles; `C` silently takes the `else` |
| `p5_getif` | `get_if`/`holds_alternative` chain; `switch (v.index())` with cases 0,1 of 3 | compiles, no diagnostic for either |
| `p6_valueless` | `emplace<Bad>` whose constructor throws | prints `valueless=1`, then `visit threw: std::visit: variant is valueless` |
| `p7_ctor` | `variant<bool,std::string> v = "abc"`; `variant<float,long> w = 0` | index 1 (string) and index 1 (long): the C++20 converting-constructor rules (no narrowing, no `const char*`→`bool`) are in effect |

**Pitfalls, ranked by how silently they fail.**
1. **The catch-all arm.** It is the variant analogue of Rust's `_ =>`. It
   compiles today and swallows alternatives added later.
2. **Conversion-reached arms.** A `[](long)` arm handles `int`, `bool` and
   `char` with no warning. Adding an `int` alternative to a variant that
   already had a `long` arm changes nothing visible.
3. **`if constexpr` chains whose last branch is not `static_assert`.**
   These are the canonical cppreference idiom, so agents will reproduce
   them.
4. **`get_if`/`holds_alternative` chains and `switch (v.index())`.** No
   exhaustiveness at all.
   - In the corpus they appear where the author clearly wanted it.
   - solidity `libyul/optimiser/Metrics.cpp:39-61` is a 10-alternative
     `holds_alternative` chain ending in
     `yulAssert(false, "If you add a new statement type, you must update CodeWeights.")`.
   - The runtime assert reconstructs what `visit` would have checked at
     compile time.
5. **The valueless state.** It is reachable only through a throwing
   type-changing assignment. P2688R6 treats it as a "residual" state (§1.5).

**Error quality is the main ergonomic cost.**
- The 72-line diagnostic is dominated by libc++ internals: `__dispatcher`,
  `__make_fmatrix_impl`, `__value_visitor`.
- It never says "no arm for `Tri`". An agent has to infer the missing
  alternative from an index.

### 1.2 An owned `match` that closes the bypasses (prototype, not design)

`probes/match.h` (about 30 lines; `match2.h` adds §5's reasoned default). The
three checks:

```cpp
template <class T> struct only {           // converts to T (cv/ref) and nothing else
  template <class U> requires std::same_as<std::remove_cvref_t<U>, T>
  operator U&() const;
};
struct unrelated {};                         // no arm can name this type
// exact arm:   std::is_invocable_v<Arms&, only<T>>  for every alternative T
// no catch-all: !std::is_invocable_v<Arms&, unrelated>
// both gate std::visit through `if constexpr`, so a failed check stops before libc++ errors
```

- **Missing arm or conversion-only arm.**
  - `only<T>` converts only to `T&`/`const T&`/`T`.
  - So an arm `[](long)` is not viable for `only<int>`, while an arm
    `[](const Circle&)` is viable for `only<Circle>`.
  - One `static_assert` per alternative gives an instantiation note that
    names the type.
- **Catch-all.** An arm that accepts a private type `unrelated` must be a
  generic (`auto`) arm.

Results:

| Probe | Input | Diagnostic |
|---|---|---|
| `m1` | visitor missing `Tri` | 23 lines, 1,726 bytes; `static assertion failed … vx::only<Tri>>': match: no arm takes this alternative exactly …`, then `in instantiation of … arm_for<…, Tri>`; one trailing secondary error (`cannot initialize return object of type 'double' with an rvalue of type 'void'`) |
| `m2` | `variant<int,bool,string>`, arms `long`, `bool`, `string` | 17 lines, names `vx::only<int>` |
| `m3` | concrete arm plus `[](const auto&)` | 11 lines, `match: an arm accepts any type (auto parameter); it would swallow alternatives added later` |
| `m4` | exact arms incl. `A&` (non-const) and `B` (by value) | compiles and runs correctly |

Compile-time cost (`ct_*.cpp`: 50 functions over a 16-alternative variant,
wall clock, one run each, noisy):

| Variant | `-fsyntax-only` | `-O2 -c` |
|---|---|---|
| `enum class` + `switch` (same headers included) | 0.06 s | 0.09 s |
| `std::visit` with overload set | 0.40 s | 0.84 s |
| prototype `vx::match` | 0.48 s | 0.92 s |

So `std::visit` costs about 7 ms per visit site at `-fsyntax-only` and
15 ms at `-O2` for 16 alternatives. The checks add about 20% on top.

**Known false findings of the prototype.**
- **Constrained generic arms.** For example `[](std::integral auto)` is not
  viable for `only<int>`, so it is reported as missing. It also is not
  viable for `unrelated`, so it is not reported as a catch-all.
- **Multi-variant visitation.** `visit(f, v1, v2)` is not handled.
- **Arms on a base class.** An arm `[](const Base&)` for an alternative
  `Derived` is rejected, because `only<Derived>` converts only to
  `Derived&`. Whether that is a false finding or the intended stop is a
  design question.
- **Rvalue-reference arms** (added by check). `vx::match(std::move(v),
  arms{[](A&&){…}, [](B&&){…}})` is rejected for both alternatives, while the
  same arms compile under `std::visit(…, std::move(v))`. `only<T>` converts
  only to an lvalue reference, which cannot bind to `T&&`.
- **Overlapping const and non-const arms** (added by check). Arms `[](A&)`
  and `[](const A&)` together make `only<A>` ambiguous, so `A` is reported
  as missing, while `std::visit` accepts the set.

### 1.3 `std::optional`, `std::expected`

Probe `ex.cpp`:

```cpp
std::expected<int,int> parse(int);
std::optional<int> find(int);
int g(int x) { parse(x); find(x); auto e = parse(x); return *e; }
```

- **The compiler is silent.** `clang++ -Wall -Wextra` gives no warning for
  the discarded `expected`, the discarded `optional`, or the unchecked `*e`.
  libc++ marks `operator*` `[[nodiscard]]`
  (`libcxx/include/__expected/expected.h:804-822`) but not the class.
- **`bugprone-unused-return-value` catches only the discarded `expected`.**
  `^::std::expected$` is in its default type list (docs
  `bugprone/unused-return-value.rst:60-62`); the discarded `optional` is not
  reported.
- **`bugprone-unchecked-optional-access` does not cover `expected`.** It is
  a flow-sensitive dataflow check over `std::optional`, `absl::optional`,
  `folly::Optional` and a few others (`unchecked-optional-access.rst`).
  Clang ships the model as
  `clang/lib/Analysis/FlowSensitive/Models/UncheckedOptionalAccessModel.cpp`,
  next to `UncheckedStatusOrAccessModel.cpp` for `absl::StatusOr`, which is
  the closest model to copy for `expected`. That model already ships as a
  clang-tidy check, `abseil-unchecked-statusor-access`
  (`clang-tools-extra/docs/clang-tidy/checks/abseil/unchecked-statusor-access.rst`).
  It treats `value()`, `operator*` and `operator->` alike and accepts an
  access only when an `ok()` check covers every path in the local scope.
  `StatusOr<T>` has the same two-state shape as `std::expected<T,E>`, so this
  is a second working template next to the optional check.

**Habit fit.**
- `optional`/`expected` are the product-of-"maybe" constructs.
- Their misuse is an unchecked access. That needs a flow-sensitive check,
  not a construct trick, because `*e` is legal syntax.
- Clang's dataflow framework already does this for `optional`. Covering
  `expected` is a model to write, not a new analysis.

### 1.4 Enums as tags

Probe `sw.cpp`:

| Flag | Fires on |
|---|---|
| default (`-Wswitch`, on) | enum switch with no `default` that misses an enumerator |
| `-Wswitch-enum` | also a switch whose `default:` hides enumerators (`enumeration values 'b' and 'c' not explicitly handled`) |
| `-Wcovered-switch-default` | a `default` in a switch that already covers every enumerator |
| `-Wswitch-default` | any switch with no `default`, including on enums (conflicts with the above) |

- Clang also has `__attribute__((enum_extensibility(closed)))` and
  `flag_enum` (`clang/include/clang/Basic/AttrDocs.td:4567-4592`). `closed`
  declares that only listed enumerators are valid values.
- `bugprone-switch-missing-default-case` covers non-enum switches only.
- Core Guidelines ES.79's enforcement note says flagging switches that miss
  enumerators "might yield too many false positives in some code bases" and
  suggests flagging only switches that handle most cases. That is the
  guideline authors' estimate, not a measurement.

**Habit fit.** An enum tag plus `-Werror=switch -Werror=switch-enum` is
already a C++ stop for finite tags. It does not tie per-tag data to the tag.
That is the gap `std::variant` fills.

### 1.5 C++ pattern matching: P2688 (and P1371)

Source: P2688R6, Michael Park, 2026-09-22,
https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p2688r6 (accessed
2026-11-23; copy in `context/scratch-adt/refs/`).

**Status.**
- Revision history R5→R6: at Hagenberg (February 2025), "Poll: [P2688R5] …
  forward to CWG for inclusion in C++26. SF 20, F 11, N 6, A 13, SA 5.
  Result: Not consensus. The proposal now targets C++29."
- §15 says the implementation is at
  https://github.com/mpark/llvm-project/tree/p2688-pattern-matching and on
  Compiler Explorer, enabled with `-fpattern-matching`.
- Clang 23.1.2 answers `clang++: error: unknown argument:
  '-fpattern-matching'`.
- P1371R3 (`inspect`) is the predecessor. P2688R6 compares against it in
  Appendix A. This lane did not read P1371 itself.

**What it specifies that matters here (§11, §11.1, §11.2).**
- "Non-exhaustiveness and redundancy are hard errors, not optional
  warnings." Guarded cases do not count toward coverage.
- **Required vs residual states.**
  - `variant` requires each advertised index; valueless-by-exception is
    residual, so a trailing `_` stays useful.
  - `optional`/`expected` have no residual state, so a trailing `_` after
    covering both is a *redundancy error*.
  - Enums require each declared enumerator value; other underlying values
    are residual.
- An unmatched non-void match on a residual state terminates. An unmatched
  void match falls through.
- **Polymorphic matching is open-world.** "Listing every currently known
  derived class is not exhaustive, so a base-class or wildcard fallback is
  still required" (§7.1, "Static Matching and Runtime").
  - So a closed hierarchy used as a sum type can never get exhaustiveness
    from C++ itself.
  - Converting it to `variant` is the only route.
- Diagnostics print source-like witnesses, e.g. `error: match expression is
  not exhaustive; example of a missing case: Quarter`. The prototype uses an
  adapted Maranget/Rust pattern-matrix algorithm.

**Habit fit.**
- Not usable this round.
- Its rule set (required vs residual, redundancy as error, guards don't
  cover, polymorphism open) is a ready-made specification for what an owned
  C++ `match` construct should enforce.
- If P2688 lands in C++29 and Clang, the construct could become a thin layer
  or be retired.

### 1.6 C++26 reflection for exhaustiveness

Probed on clang 23.1.2:
- `-freflection`: "argument unused during compilation".
- `<meta>`: `fatal error: 'meta' file not found`.
- `-Xclang -freflection` with `^^E` for an enum: "unknown or unimplemented
  reflectable entity". `^^int` is "not a constant expression".
- Expansion statements: `template for (auto x : std::tuple{1,2,3})` compiles
  and runs (exit 6), but `__cpp_expansion_statements` is not defined.

This matches `papers/2026-10-17-cpp26-clang-toolchain.md`: upstream
reflection is landing piecemeal, and only the bloomberg/clang-p2996 fork
implements P2996.

**Consequences for this habit.**
- **Variant exhaustiveness does not need reflection.** The alternative list
  is a type pack (§1.2 uses it directly).
- **Enum exhaustiveness at library level does need an enumerator list.**
  On clang 23.1.2 that means one of:
  - `-Wswitch`;
  - a declaration macro that also emits the list;
  - magic_enum's `__PRETTY_FUNCTION__` scan, which the 2026-10-17
    reference-implementations paper marks "to avoid".
- **Compile-time structural checks on aggregates need reflection.** An
  example is "this struct has 4 bools". On this toolchain they belong in an
  AST tool, not in the library.

### 1.7 Library sum types in quarantine

type_safe (`quarantine/type_safe`, commit
`292e8c127037e33d92f8f52dab0f1184993942d0`):

- **`basic_variant<Policy, Ts...>` puts the exception-safety choice in a
  policy** (`include/type_safe/variant.hpp:36-49`):
  - `fallback_variant_policy` puts a nothrow fallback type in place on
    failure (`:762`);
  - `optional_variant_policy` gives an explicit empty state, `nullvar`
    (`:822`);
  - `rarely_empty_variant_policy` and `never_empty_variant_policy` (`:895`,
    `:902`).

  `ts::variant<nullvar_t, Ts...>` selects the optional policy (`:931`). This
  is a construct-level answer to `valueless_by_exception`: name the empty
  state, or forbid it.
- **`visit` is exhaustive by default.** It does
  `static_assert(... "visitor does not cover all possible combinations")`
  (`visitor.hpp:68`, `:190`).
- **There is an explicit opt-out**: a member named `incomplete_visitor` on
  the visitor (`visitor.hpp:117-121`, documented `:151`, `:393`). That is a
  way past at the construct, but it carries no reason.
- **`with(variant, f)` silently does nothing when `f` is not callable for
  the active type** (`variant.hpp:719-749`; `tagged_union.hpp:309-336`).
  - This is the library-provided form of the catch-all bypass.
  - A verbs construct should not offer it, or should require the same
    reason as an `otherwise` arm.

Other quarantine entries touch adjacent habits:
- sml and msm: state machines (another lane);
- NamedType and strong_type: product and newtype wrappers.

None of them adds exhaustiveness machinery beyond what is above.

## 2. Rust

### 2.1 Enums, exhaustive `match`, `#[non_exhaustive]`

- **A non-exhaustive `match` on an enum is a hard compile error** (E0004).
  The rustc diagnostic lists missing patterns.
- **`#[non_exhaustive]` on an enum forces a wildcard arm in other crates.**
  Inside the defining crate it has no effect.
- **The lint that would tell a downstream crate which known variants its
  wildcard swallows is unstable.** It is `non_exhaustive_omitted_patterns`,
  behind `feature(non_exhaustive_omitted_patterns_lint)`, tracking issue
  rust-lang/rust#89554; no stabilization was found.
  - Status at check (https://github.com/rust-lang/rust/issues/89554, fetched
    2026-11-23): open, labelled `S-tracking-ready-to-stabilize`, and no
    stabilization PR is linked. Unresolved items listed there are the lint's
    name and message. A pattern-exhaustiveness maintainer (Nadrieril,
    2025-11-30) wrote that it "would fit better as a clippy lint" now that
    the exhaustiveness logic is a reusable crate. So stable support may
    arrive as a clippy lint rather than a rustc one.
  - On stable 1.99.1: `warning: unknown lint: non_exhaustive_omitted_patterns`.
  - On `nightly-2026-08-21` with the feature, the following match:

    ```rust
    match o { std::io::ErrorKind::NotFound => 1, _ => 0 }
    ```

    gives `patterns ErrorKind::PermissionDenied, ErrorKind::ConnectionRefused,
    ErrorKind::ConnectionReset and 35 more not covered`.

### 2.2 Clippy lints that push toward ADTs (verified on clippy 0.1.99)

Two probe crates were run (`probes/clippy_probe2.rs` is the second; the
first is described inline).

| `match_same_arms` | pedantic | identical arm bodies | fired (check probe) |
| `match_wild_err_arm` (added by check) | pedantic | `Err(_) => panic!(..)`: a catch-all over every error alternative that panics | fired: "`Err(_)` matches all errors" |
| `wildcard_in_or_patterns` (added by check) | style, on by default | `A(_) \| _ =>` | fired: "wildcard pattern covers any other pattern as it will match anyway" |
| `clippy::unreachable`, `clippy::panic` (added by check) | restriction | any `unreachable!`/`panic!` | fired on `_ => unreachable!()` and `Err(_) => panic!` |
| rustc `unreachable_patterns` (added by check) | rustc, warn by default | `_` after arms that already cover every variant | fired ("unreachable pattern"). This is P2688's "redundancy" rule, but as a warning, not an error |

Configuration text is from https://doc.rust-lang.org/clippy/lint_configuration.html,
accessed 2026-11-23. It lists `option_option` and `ref_option` among the 19
lints that `avoid-breaking-exported-api` suppresses.

**`#[expect(lint, reason = "...")]`** was stabilized in Rust 1.81 (RFC 2383,
rust-lang/rust#120924; https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/).
In the probe, `#[expect(clippy::needless_return, reason = "...")]` on code
that does not trigger it produced `warning: this lint expectation is
unfulfilled`. That is Rust's built-in stale-reason detector.

**Gaps (nothing fired even with every restriction lint on):**
- **An `if let` / `matches!` chain over enum variants with a fallback.**

  ```rust
  if let Cmd::A(x) = c { return *x; }
  if matches!(c, Cmd::B(_)) { return 2; }
  0
  ```

  This is the Rust analogue of the C++ `get_if` chain.
- **Stringly dispatch.** `match s { "circle" => 1, "square" => 2, _ => 0 }`.
- **A sentinel `-1` return** from a search function.
- **Several `Option` fields always set together.**
- **`dyn Any` / `downcast_ref` chains** used as a closed sum. The check
  probed one (`if x.downcast_ref::<u32>().is_some() {…} else if
  x.downcast_ref::<String>()…`) with every pedantic and restriction lint on
  (clippy 0.1.99 from 1.99.1). Nothing fired. The string dispatch, `-1` sentinel and
  two-`Option` struct above were also silent in the same run.

  `papers/li-2024-unleashing-clippy-real-world-rust-icse-poster.pdf`).
  - Over crates.io, more than 50% of warnings come from the top-1 lint and

  - Survey respondents name false positives and missing auto-fix as the

### 3.2 Tag field plus union; tag plus fields valid only for some tags

**Existing lints.**
- **`bugprone-tagged-union-member-count`** (docs
  `clang-tools-extra/docs/clang-tidy/checks/bugprone/tagged-union-member-count.rst`;
  source `bugprone/TaggedUnionMemberCountCheck.cpp`, 192 lines).
  - Its definition of a tagged union is structural: a record with exactly
    one union data member, exactly one enum data member, and no other
    union or enum members, with system-header and `std` types excluded.
  - It only reports a *count mismatch* between union members and distinct
    enum values. It uses a heuristic for `…Count` sentinel enumerators.
- **`cppcoreguidelines-pro-type-union-access`** flags *every* union member
  access. That is a blanket rule, not evidence of misuse.
- **Core Guidelines.** C.181 ("Avoid naked unions") and C.182 ("Use
  anonymous unions to implement tagged unions") say what to do. C.181's
  enforcement is "???".

**Measured (`tagged` matcher: a record with any enum-typed field and any
union-typed field).**
- There were 10 distinct first-party matches, and **all 10 are tagged
  unions on reading**:
  - abseil `flags/internal/flag.h:208` (`FlagHelpArg`) and `:266`
    (`FlagDefaultArg`);
  - duckdb `column_data_allocator.hpp:40`;
  - rocksdb `table/get_context.h:70` and PerconaFT `db.h:39`;
  - llama.cpp `common/json.h:42` (`common_json_value`) and
    `include/llama.h:302` (`llama_model_kv_override`);
  - protobuf `extension_set.h:123` (`ExtensionInfo`),
    `generated_message_tctable_gen.h:196` (`AuxEntry`) and
    `map_field.h:77` (`MapKey`).
- **For several, the remedy has a real reason to be declined:**
  - `llama.h` and PerconaFT `db.h` are C headers (C ABI);
  - protobuf's table-generation `AuxEntry` and abseil's flag args are
    constexpr, trivially copyable layout-sensitive data. `std::variant` is
    constexpr in C++20 but not trivially copyable when alternatives are not.
- **One match also has fields valid only for some tags, outside the
  union.** `common_json_value` has `VAL_STRING` and `VAL_JSON` tags whose
  payloads are not union members. That is the "tag plus fields valid for
  some tags" pattern. Detecting the full pattern needs to know which fields
  are read under which tag test: a guard-and-access analysis, not a
  declaration shape.

**Literature with numbers.** Hong & Ryu, "To Tag, or Not to Tag: Translating
C's Unions to Rust's Tagged Unions," ASE 2024, arXiv 2408.11418v2
(`papers/hong-ryu-2024-to-tag-or-not-to-tag-c-unions-rust-ase.pdf`).
- **Method.**
  - Urcrat identifies, for each union, the struct field that acts as its
    tag and the tag value associated with each union field.
  - It combines a may-points-to analysis, the values written to candidate
    fields, and `switch`/`if` guards on the tag before union-field reads.
  - It then rewrites C2Rust output to Rust enums.
- **§5.3 (RQ1).** 141 candidate unions across 36 programs; tag fields found
  for 74. On manual inspection: **no false positives and 5 false
  negatives**, i.e. precision 100% and recall 93.7% (74/79).
  - The false negatives come from intermediate tag states, a `goto`-induced
    path-insensitivity, and a real bug in uucp, where the wrong field is
    read.
- **§5.4.** 17 of 23 programs with tests still pass after the
  transformation. The failures come from reading a union field other than
  the last-written one, memory-layout dependence, and missing
  inter-procedural or library modeling (gawk, twemproxy).
- **§5.5.** Most programs take under a minute. gawk took **4,910 s**.
- **Bearing on verbs.**
  - The declaration shape alone is near-certain evidence of a tagged union.
  - The tag-to-field mapping, needed for a correct rewrite or for a
    "wrong field read under tag" stop, needs whole-program points-to
    analysis. That is far beyond an edit-time check.
  - The wrong-field reads Urcrat trips over (grep, make) are exactly the
    bugs a variant would have prevented.

### 3.3 Sentinel values (`-1`, empty string, `nullptr` meaning "absent")

**Existing lints.**
- No clang-tidy or clippy lint for in-band sentinels was found.
- CERT ERR02-C, "Avoid in-band error indicators," is a guideline with
  "Automated detection" left to vendors
  (https://wiki.sei.cmu.edu/confluence/spaces/c/pages/87152400, via search
  2026-11-23).
- `bugprone-unused-return-value` covers discarded return codes, not
  sentinel *types*.

**Measured.** Text counts of `== -1` / `!= -1` / `return -1;` range from 8
(leveldb) to 390 (llama.cpp). The count does not separate a sentinel from a
legitimate `-1`, so it is not a precision figure.

**Literature.**
- **DeFreez et al., "Effective Error-Specification Inference via
  Domain-Knowledge Expansion," ESEC/FSE 2019**
  (`papers/defreez-2019-eesi-error-specification-inference-fse.pdf`).
  - EESI infers the set of values each C function returns on error, from
    seed domain knowledge plus intraprocedural flow-sensitive and
    interprocedural context-insensitive analysis.
  - It estimates **precision 0.93** for the inferred specifications.
  - Its bug finder ECC reported 246 bugs in 9 programs, 110 of them
    confirmed.
  - It took 5 min 25 s on 320K lines of Linux file-system code.
  - This is the strongest prior art for recognizing "this return value is
    a sentinel". Its unit of evidence is the *function's error convention*,
    not a lexical `-1`.
- **Hong & Ryu, "Don't Write, but Return: Replacing Output Parameters with
  Algebraic Data Types in C-to-Rust Translation," PLDI 2024 (PACMPL 8,
  PLDI, 716–740, doi 10.1145/3656406).**
  - The program page reports 1,670 output parameters detected across 55
    programs (190k LOC in 213 s), rewritten to tuples and `Option`.
  - The PDF was not obtainable (ACM returned 403), so the paper's precision
    figures were **not read**.

**Habit fit.**
- `std::optional`/`std::expected` (C++) and `Option`/`Result` (Rust) are
  the constructs.
- Stopping on sentinels needs evidence that the value is used as "absent",
  for example a comparison against the same constant at every call site.
  That is a fact-extractor job, with EESI as the model.

### 3.4 Parallel optionals set together

**Existing lints.** None in clang-tidy or clippy.

**Detection literature.** None found that targets this pattern.

**Measured.** Records with 2 or more `std::optional` fields: solidity 17,
rocksdb 6, duckdb 3, others at most 1. Whether the fields are set together
is a write-site fact this lane did not extract. The older encoding of the
same idea, `has_X_` bool plus `X_` field, appears in rocksdb `VersionEdit`
(§3.1).

**Possible evidence source.** A co-occurrence invariant such as "`a` is
engaged iff `b` is engaged" is a dynamic-invariant template. Daikon's
implication invariants (`papers/ernst-2007-daikon-system-scp.pdf`) are the
nearest machinery. A static version would need "set in the same statement
group, cleared together" facts. This lane did not test either.

### 3.5 Stringly-typed variants

**Existing lints.** None in clang-tidy or clippy (§2.2 probe: `match s {
"circle" => …}` is silent).

**Measured.** 39 first-party string variables are compared against 3 or
more literals: btop 13, duckdb 9, llama.cpp 12, rocksdb 3, protobuf 2.

A first-pass read (declaration plus enclosing function, not a validated
label) splits them as follows:
- **About 10–12 carry an internal variant as a string.** Examples:
  - btop `btop.cpp:732` `run(const string& box, …)` with `box` in
    {`"cpu"`, `"mem"`, `"net"`, `"proc"`};
  - btop `btop_tools.cpp:638` `celsius_to(…, const string& scale)`;

### 3.6 Inheritance used as a closed sum (`dynamic_cast`/`typeid` switching)

**Existing lints.**
- `cppcoreguidelines-pro-type-static-cast-downcast` flags `static_cast`
  downcasts only.
- Core Guidelines C.153 ("Prefer virtual function to casting") gives
  enforcement as "See C.146 and ???".
- No clang-tidy check reports `dynamic_cast` chains or `typeid` comparisons.
- The `llvm-type-switch-case-types` check concerns LLVM's own `TypeSwitch`
  spelling, not this pattern.

**Measured.**
- solidity: 59 `dynamic_cast` sites in the 60 sampled TUs (1,280 textual in
  all of solidity) and 3 `if`/`else if` chains, e.g.
  `libsolidity/analysis/ConstantEvaluator.cpp:320` and
  `codegen/ContractCompiler.cpp:274`.
- llama.cpp: 14 sites. Other projects: 0 in the sample.

**What can be said with evidence.** P2688R6 states that polymorphic
matching cannot be exhaustive (§1.5). So the only way to get compile-time
exhaustiveness for a closed set of subclasses in C++ is to change
representation to `variant`, or to add a visitor interface. A chain of
`dynamic_cast` ending in an assert/throw/unreachable is explicit evidence
that the author believes the set is closed.

**Literature.**
- **Tsantalis, Chaikalis & Chatzigeorgiou, "JDeodorant: Identification and
  Removal of Type-Checking Bad Smells," CSMR 2008, pp. 329–331.** It
  detects type-code conditionals and RTTI (`instanceof`) chains in Java and
  proposes "Replace Conditional with Polymorphism". The evaluation is in
  Tsantalis & Chatzigeorgiou, JSS 83(3):391–404, 2010. Neither was read:
  the host refused connection. **No precision figure is reported here.**
- **Mastrangelo, Hauswirth & Nystrom, "Casting about in the Dark," OOPSLA
  2019** (doi 10.1145/3360584). Its abstract (via search; ACM returned 403)
  reports casts in 8.7% of methods over 7,559 Java projects, 50% of
  inspected casts not guarded locally, and 25 cast usage patterns. The
  "26" sometimes cited is a citing paper's miscount.
- **The same study in full** (added by check). Mastrangelo's dissertation,
  "When and How Java Developers Give Up Static Type Safety" (USI, June 2019),
  ch. 4
  (`papers/mastrangelo-2019-when-how-java-developers-give-up-static-type-safety-usi-phd.pdf`).
  - Of 5,000 sampled casts, **Typecase**, meaning dispatch on the runtime
    type, is the most common pattern: 1,182 casts (23.64%, Table 4.2).
  - Figure 4.4 splits it by guard: `instanceof` 881, an
    application-specific type tag 237, class-literal comparison 64. The
    type-tag variant is the Java form of §3.2's tag field.
  - §4.5.1: "In the 742 instances of Typecase that used instanceof, 511
    (69%) had only one case."
  - For verbs, a downcast site is usually *not* a closed-sum dispatch. Only
    multi-case chains are candidates, so a guard keyed on `dynamic_cast`
    count alone would mostly report single-case downcasts.
  - The labels are the authors' manual categorisation, which they call
    "subjective".
- **Java's answer to the open-world rule** (added by check). JEP 441
  (https://openjdk.org/jeps/441, fetched 2026-11-23; delivered in Java 21)
  says: "If the type of the selector expression is a sealed class (JEP 409)
  then the type coverage check can take into account the permits clause".
  An unmatched value at run time throws `MatchException`. Java gets
  exhaustive matching over a class hierarchy by letting the base class
  declare its subclasses. C++ has no `permits` clause, which is why P2688
  must call polymorphic matching open-world. For a verbs C++ construct, the
  nearest equivalent is a base that names its derived types in a type list,
  which then amounts to a `variant`.

### 3.7 Misuse of the construct itself (summary of evidence strength)

| Misuse | C++ today | Rust today | Evidence that it is wrong when present |
|---|---|---|---|
| visitor missing an alternative | compile error (poor message, §1.1) | E0004 | certain (language) |
| catch-all arm (`auto` / `_`) | silent | `wildcard_enum_match_arm` (restriction) | intent-dependent; a deliberate default is common (solidity `OptimizedEVMCodeTransform.cpp:251` `[](auto const&) { return YulName{}; }`) |
| catch-all arm whose body asserts/throws/unreachable | silent | not specifically: under `-W clippy::restriction`, `_ => unreachable!()` draws `wildcard_enum_match_arm` (as any `_` does) and `clippy::unreachable` (as any `unreachable!` does); no lint ties the two together (check probe, clippy 0.1.99) | strong: author asserts the case cannot occur. Either list the alternatives (compile-time) or the type is wider than the invariant. solidity `ControlFlowGraphBuilder.cpp:328`: `[&](auto const&) { yulAssert(false, ""); }`, where only `FunctionCall` is legal: a narrower type is the real remedy |
| arm reached only by implicit conversion | silent | n/a (no implicit conversion) | strong: no user writes `[](long)` to mean `bool` |

## 4. Seeded faults for these guards

**The canonical fault.** For this habit it is "a new alternative appears".
- Add an alternative to a `std::variant`, an enumerator to an enum, or a
  variant to a Rust enum.
- The guard's claim is checkable: every dispatch site over that type either
  fails to compile with a diagnostic naming the new alternative, or carries a
  recorded reason (an `otherwise` arm, `_ =>` with `#[expect]`).
- **The oracle is the expected-diagnostic set.** It is the same style the
  reference-implementations lane recorded for IWYU, CodeQL and mp-units
  (`2026-10-17-reference-implementations.md`).

**Further mutation operators, all source-level:**
- replace an exact arm's parameter type with a type it converts from
  (`const Square&` → `long` where applicable);
- insert a catch-all arm;
- delete an arm;
- rewrite a `visit` into an equivalent `holds_alternative` chain with a
  default return;
- swap the order of alternatives in a variant that is dispatched through
  `.index()`;
- in Rust, replace one explicit arm with `_`.

**Corpora where this bites.**
- solidity: 149 `visit`, 190 `holds_alternative`, 95 `get_if` over the Yul
  AST variants.
- abseil: 67 `std::variant`.
- rocksdb: 47 `std::variant`.
- These give real dispatch sites to seed. The census shows most other
  projects barely use `variant`, so the sum-type guards will be tested
  mostly on those three plus agent-written code.

**Tooling cost.**
- Mull (`quarantine/mull`) mutates IR and AST expressions. It has no
  type-level edit such as "add an alternative".
- cargo-mutants (Rust; https://mutants.rs/mutants.html, fetched 2026-11-23,
  added by check) has two match operators:
  - it deletes whole match arms, but "when a wildcard pattern is present in
    one of the arms", and skips matches without one as "too prone to
    unviable mutations";
  - it replaces match guards with `true` and `false`.

  Both test run-time behaviour through tests. Neither adds a variant, so
  this guard's canonical fault still needs an owned mutator in Rust too.
- These operators are textual or `clang::Rewriter` edits on declarations
  plus a rebuild of affected TUs. Rebuild cost dominates: §1.2's numbers
  put a variant-heavy TU at a fraction of a second, but solidity TUs failed
  to configure without generated headers (41/60 fatal).
- `Just et al. 2014` (`papers/just-2014-mutants-valid-substitute-real-faults-fse.pdf`)
  is the standing justification for mutants as fault proxies. Its evidence
  concerns test suites, not compile-time guards.

## 5. Way past every finding, with a recorded reason

**Rust.**
- `#[expect(lint, reason = "...")]` is stable (1.81).
- An expectation that no longer matches produces
  `unfulfilled_lint_expectations` (verified, §2.2).
- `clippy::allow_attributes_without_reason` and `clippy::allow_attributes`
  force reasons and push `allow` to `expect`.
- **This is a complete mechanism already.** The only missing piece is
  checking reason quality.

**C++ lint level.**
- **clang-tidy `NOLINT(check)`** accepts a free-text tail by convention
  (docs: `// NOLINT: Allow implicit conversion from char, because <some
  valid reason>`, `clang-tidy/index.rst:526-575`). The tail is not required
  or parsed.
- **Unused `NOLINT` is not detected.** A grep of `clang-tidy/*.cpp` and
  `clang-tidy/tool/*.cpp` in 23.1.2 found no unused-NOLINT reporting.
- **`[[clang::suppress]]` / `[[gsl::suppress("...")]]`** (`Attr.td:3496`)
  suppresses static-analyzer findings. Its docs say it "cannot be used to
  suppress traditional Clang warnings" (`AttrDocs.td:6639-6643`).
- **`#pragma clang diagnostic`** carries no reason.

**C++ construct level** (prototype `probes/match2.h`, `o1`–`o3`):
- `vx::otherwise<"reason">(f)` is the only way to write a default arm. The
  reason is a non-type template argument (a string literal), so it lives in
  the code at the site.
- **Stale reason.** If every alternative already has an exact arm, the
  `otherwise` arm is dead. A `static_assert` reports `match: stale otherwise
  -- every alternative has an exact arm; delete the otherwise arm and its
  reason` (probe `o2`). This is the construct-level equivalent of
  `unfulfilled_lint_expectations`, decided entirely at compile time.
- **Empty reason.** A reason shorter than 8 characters fails `otherwise:
  give a reason` (`match2.h` asserts `sizeof(R.s) > 8`; probe `o3` uses the
  one-character reason `"x"`). A length check is a gate, not a quality
  judgement.
- **Normal use.** `o1` compiles and dispatches correctly: `B` reaches the
  default.

**Precedents in other languages** (added by check). These are not targets
this round, but each is a working way past a catch-all:
- **typescript-eslint `switch-exhaustiveness-check`**
  (https://typescript-eslint.io/rules/switch-exhaustiveness-check, fetched
  2026-11-23).
  - `considerDefaultExhaustiveForUnions` is off by default, so a `default`
    does not count as covering union members. The docs say keeping it off
    makes "sure every value added to the union receives explicit handling".
  - `defaultCaseCommentPattern` (default `/^no default$/iu`) is a "Regular
    expression for a comment that can indicate an intentionally omitted
    default case". A comment pattern stands in for the clause.
  - `allowDefaultCaseForExhaustiveSwitch: false` reports a `default` on a
    switch that already covers every member. That is the same staleness
    rule as `o2` above.
- **Swift `@unknown default`** (SE-0192, implemented in Swift 5.0;
  https://github.com/swiftlang/swift-evolution/blob/main/proposals/0192-non-exhaustive-enums.md,
  fetched 2026-11-23).
  - It is a catch-all that still makes the compiler "produce a *warning* if
    all known elements of the enum have not already been matched".
  - It is a warning, not an error, "so that adding new elements to the enum
    remains a source-compatible change".
  - This is the stable-language form of Rust's unstable
    `non_exhaustive_omitted_patterns`, and the closest precedent for a
    reasoned default that still reports new alternatives.

**Agent ergonomics.** Agents clear lint failures by inline suppression,
config downgrade or file exclusion (practitioner reports collected in
`2026-10-17-literature-agent-feedback.md` §2; no peer-reviewed
measurement).
- For this habit, the zero-cost bypasses are a catch-all arm in C++ and
  `_ =>` in Rust. No suppression comment is needed, so a suppression audit
  never sees them.
- Making the catch-all itself the thing that needs a reason (the C++
  construct above; `wildcard_enum_match_arm` plus `#[expect(..., reason)]`
  in Rust) moves the bypass into the audited channel.

## 6. Costs and failure modes

- **Compile time.** About 7 ms per `std::visit` site (`-fsyntax-only`) and
  15 ms at `-O2` for 16 alternatives, against about 1 ms for an enum
  switch. The construct checks add about 20%. Visits nested over several
  variants grow as the product of alternative counts; this was not
  measured.
- **Diagnostics.**
  - Raw `visit` errors are 10 KB of libc++ internals.
  - The construct's errors are under 2 KB and name the type, but still
    print lambda locations (`(lambda at m1.cpp:6:5)`), not arm text.
  - libc++ internals change between releases, so any check that matches on
    their text is brittle. Owned `static_assert` messages are not.
- **Layout and ABI.**
  - `std::variant` is not usable in C headers.
  - It is not trivially copyable when an alternative is not.
  - It carries an index whose size the implementation picks.
  - These are the recurring legitimate reasons in §3.2. A nudge here needs
    a reason channel; a stop would be wrong.
- **Valueless state.** A type-changing assignment that throws leaves a
  `std::variant` valueless, and later `visit`s throw. A construct either
  inherits this or adopts a policy (type_safe's `never_empty`/`optional`
  policies).
- **Prototype false findings** (§1.2): constrained generic arms, base-class
  arms, multi-variant visitation.
- **Clippy.**
  - Pedantic and restriction lints need explicit enabling.
  - `option_option`/`ref_option` go quiet on `pub` items unless
    `avoid-breaking-exported-api = false`.
  - `wildcard_enum_match_arm` on a `#[non_exhaustive]` foreign enum
    suggests listing every variant plus `_`: 40 names for `io::ErrorKind`.
    The stable compiler cannot tell the reader which ones were missed.
- **Toolchain.** Reflection and pattern matching are absent on the pinned
  compiler, so nothing in this habit can depend on them this round.
- **AST census caveats.**
  - The rewritten compile databases lack generated headers, which produced
    the fatal counts in §3.0.
  - One matcher artifact: closure types count as records.
  - Duplicate path spellings.
  - A verbs check would run on a real build tree and avoid all three.

## What this means for verbs

The options this lane opens, ranked.

1. **Own a C++ `match` over `std::variant`; in Rust, configure rather than
   build.**
   - C++: the construct makes three bypasses compile errors at the site,
     each naming the alternative: missing arm, conversion-only arm and
     catch-all. Its only default is a reasoned `otherwise` whose staleness
     is checked at compile time.
   - Rust: set rustc's E0004 plus `wildcard_enum_match_arm`,
     `match_wildcard_for_single_variants`, `struct_excessive_bools`,
     `allow_attributes_without_reason` and `#[expect]` to the levels the
     operator wants.
   - Reason for the rank: it is the strongest evidence class (language
     semantics), it needs no fact extraction, and it was demonstrated here.
     Every C++ finding it makes is about the construct, so the false-finding
     surface is the three cases in §1.2.
2. **Misuse stops with explicit-intent evidence**, as C++ AST checks.
   - The checks:
     - a `holds_alternative`/`get_if` chain or `if constexpr` chain over a
       variant whose final branch asserts, throws or is unreachable;
     - a catch-all arm whose body asserts;
     - `switch (v.index())`;
     - `default:` hiding enumerators (`-Wswitch-enum`, which exists);
     - unchecked `*expected` / `.value()`, by extending the
       `UncheckedOptionalAccessModel` pattern or cloning
       `UncheckedStatusOrAccessModel`.
   - Rust has the same gap for `if let` chains ending in `unreachable!`.
   - Each has a concrete corpus exhibit (solidity), and the author's own
     assert states the intent.
   - The catch-all-that-asserts case may point to "the type is too wide"
     rather than "list the alternatives", so its message must not prescribe
     a single fix.
3. **Nudges for "should have been an ADT"**, ordered by measured evidence:
   - **(a) enum-field-plus-union record.** 10/10 true here, consistent with
     Urcrat's 0 false positives on the tag-field question. The remedy is
     often declined for C ABI or layout reasons, so it is a nudge with a
     reason channel, not a stop.
   - **(b) name-paired fields:** `has_X`/`X`, `X`/`auto_X`,
     `is_Xing`/`is_Xed`, `XSet`/`X`. Untested as a rule; the cases surfaced
     inside the bool sample.
   - **(c) bool count above 3.** About 28% contain a mode or state
     sub-cluster. Keep it only if the operator wants clippy parity as an
     "always accept" rule. It is not ADT evidence.
   - **(d) strings compared against 3+ literals.** About 25–30% raw. Only
     worth showing if a "crossed an internal call" filter lifts it.
   - **(e) sentinels and parallel optionals.** No usable detector without
     EESI-style error-convention or co-write facts. Defer to the
     fact-extraction lane.
4. **A seeded-fault harness built on "add an alternative"** over solidity,
   abseil and rocksdb dispatch sites, plus agent-written code. The oracle is
   exact: every site fails with the named alternative, or carries a reason.
   It needs an owned source mutator; Mull does not cover type edits.
5. **Defer:**
   - P2688 pattern matching (C++29, fork-only);
   - reflection-based enum exhaustiveness (fork-only on this machine);
   - whole-program tag inference à la Urcrat (points-to; 4,910 s worst
     case);
   - `dynamic_cast`-chain conversion to `variant`. The open-world rule
     means no C++ mechanism can certify a hierarchy closed; a chain ending
     in an assert is the only strong signal, and it belongs in option 2.

## Open questions

1. **Wrap or own the sum type?** Should the C++ construct wrap
   `std::variant` (as prototyped) or be its own sum type? An own type could
   fix the valueless state by policy, carry names for alternatives and hold
   reasons, at the cost of interop with code that takes `std::variant`.
2. **Base-class arms.** Is an arm taking a base class of an alternative a
   finding (stop) or allowed? Does a constrained generic arm count as
   exact, as a catch-all, or as neither?
3. **Where is a deliberate default allowed?** In Rust and in the C++
   construct alike: always with a reason, never, or only for
   `#[non_exhaustive]` and foreign types? How should the absence of
   `non_exhaustive_omitted_patterns` on stable be handled?
4. **What counts as a reason?** The construct can check presence, length and
   staleness at compile time, but not content. Is a recorded reason ever
   reviewed by anything but a human?
5. **How are bool sub-clusters and parallel optionals evidenced?** By names
   (a guess, per the enum lane), by co-write and mutual-exclusion facts
   (needs an extractor and a precision run on held-out code), or not at
   all?
6. **Stop or nudge for the explicit-intent misuses?** For example a chain
   ending in an assert. Is "the author asserted exhaustiveness" evidence
   strong enough to be a default error, given that the right fix may be a
   narrower type rather than more arms?
7. **The `std::expected` unchecked-access check.** Should verbs carry its
   own dataflow model, or contribute it upstream to clang-tidy and wait?
   This bears on the no-runtime-dependency rule only through the toolchain.
8. **Diagnostics through the agent loop.** Does the agent feedback channel
   pass compiler `static_assert` text through verbatim? A message naming
   `only<Tri>` is good only if the agent sees it before the libc++ notes.
9. **Is this round's evidence enough?** The precision figures here come
   from one reader on 8 projects, with no second rater. Does the design need
   a labeled, held-out set before any nudge ships, as the enum lane
   concluded for its own rule?

### Added

- **Two more prototype false findings (§1.2), both reproduced.** Rvalue-ref
  arms on `match(std::move(v), …)` are rejected, and overlapping `A&` and
  `const A&` arms are reported as missing. `std::visit` accepts both.
- **`abseil-unchecked-statusor-access` (§1.3).** It is a shipped clang-tidy
  check over the StatusOr model, a direct template for an `expected` check.
- **Clippy and rustc lints (§2.2).**
  - `match_wild_err_arm` (pedantic, `Err(_) => panic!`);
  - `wildcard_in_or_patterns` (style, on by default);
  - `clippy::unreachable` and `clippy::panic` (restriction);
  - rustc `unreachable_patterns`, warn by default: P2688's redundancy rule
    at warning strength.

  All were probed. The `dyn Any` downcast chain was probed and is silent.
- **`non_exhaustive_omitted_patterns` status (§2.1).** The issue is open
  and labelled ready-to-stabilize. A maintainer suggests it belongs in
  clippy.
- **clang-tidy 23.1.2 removed the `hicpp` module** (`docs/ReleaseNotes.rst:62`).
  `hicpp-multiway-paths-covered` is now `bugprone-unhandled-code-paths` plus
  `readability-trivial-switch`. Configurations written for older clang-tidy
  that name `hicpp-*` will not find those checks.
- **Sonar RSPEC-6000**, "std::visit should be used to switch on the type
  of the current value in a std::variant". This is the only existing lint
  found that targets `index()` switches and `holds_alternative`/`get_if`
  chains as such.
  - Source: search snippets of rules.sonarsource.com, 2026-11-23. The rule
    pages now redirect to a client-rendered page, so the full text was not
    read.
  - Related Sonar rules: RSPEC-6025 ("Use std::variant instead of unions
    with non-trivial types") and RSPEC-7147 (union use).
  - Sonar is proprietary, so this is prior art for the rule, not a
    candidate dependency. No precision data was found.
- **Casts as closed sums (§3.6).** Mastrangelo's dissertation (now in
  `papers/`) gives the only frequency data found for this pattern.
  - Typecase is 23.64% of 5,000 sampled Java casts.
  - 69% of `instanceof` Typecases have a single case.
  - 237 are guarded by an application type tag.

  A guard should therefore key on multi-case chains, not on downcast sites.
- **JEP 441 (§3.6).** Sealed `permits` lets Java check exhaustiveness over a
  class hierarchy. It is the cross-language contrast to P2688's open-world
  rule; the lane had listed it as unobtained.
- **Way-past precedents (§5).** typescript-eslint's
  `defaultCaseCommentPattern`, `considerDefaultExhaustiveForUnions` (off by
  default) and `allowDefaultCaseForExhaustiveSwitch: false` (a staleness
  rule). Swift's `@unknown default` keeps the catch-all but still warns on
  newly known cases.
- **cargo-mutants match operators (§4).** It deletes arms only when a
  wildcard is present, and it flips guards. Neither adds a variant.
